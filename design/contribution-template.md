# 内容贡献模板

> [INPUT]: `content.json` 的概念、资源、关系、入口与来源接口，以及 `sources.md` 的核对记录。
> [OUTPUT]: 新增资源、改写概念、修正关系和提交 PR 的填写说明。
> [POS]: `design/` 的贡献入口；字段映射到唯一内容正本，不保存第二份资源正文。
> [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md

先在 [content.json](content.json) 搜索名称与 ID，确认是否已经存在同一对象。已存在时直接改正本，或让新入口引用该 ID。完整样例为资源 `sqlite` / `postgresql`，概念 `data-storage`，比较关系 `sqlite-postgresql-comparison`。

下面的中文提示可先用于 issue 或 PR 草稿。进入样板的数据按对应字段写入 JSON；数组中的每条内容独立填写，不把逗号分隔的文字当作数组。

## 资源条目

| 写什么 | JSON 字段 | 填写说明 |
|---|---|---|
| 稳定标识 | `id` | 不与已有概念或资源重复，不含空格；三入口引用这个 ID。 |
| 名称 | `name` | 官方项目名，不为不同入口改名。 |
| 类型 | `kind` | 帮读者分清它是库、框架、数据库系统、工具等什么对象。 |
| 一句话定位 | `summary` | 先说它帮软件做什么。 |
| 用途 | `purpose` | 哪种具体问题会用到它。 |
| 运行环境 | `environment` | 它在哪里运行，与调用它的程序如何配合。 |
| 使用条件 | `requirements[]` | 是否需安装、服务、驱动、账号或托管；只写实际适用的条件。 |
| 限制与边界 | `limits[]` | 哪些情况要重新评估，避免无条件宣称适合或不适合。 |
| 官方入口 | `officialUrl` | 项目官网或官方项目页的完整链接。 |
| 依据 | `sourceIds[]` | 引用 `sources` 中的 ID，核对说明写在 `sources.md`。 |
| 核对日期 | `verifiedAt` | 实际核对日期，格式为 `YYYY-MM-DD`。 |
| 概念归属 | `conceptIds[]` | 引用已经存在的概念 ID，不粘贴概念正文。 |

如果事实尚未查清，可先在 issue 或 PR 说明缺口，不要用猜测填成已核实条目。

## 概念条目

| 写什么 | JSON 字段 | 填写说明 |
|---|---|---|
| 标识与名称 | `id`、`name` | 给概念稳定身份，与具体项目分开。 |
| 一句话定位 | `summary` | 它负责什么。 |
| 起源问题 | `why` | 没有它时会遇到什么困难，尽量给具体情境。 |
| 机制 | `mechanism` | 它如何起作用。 |
| 边界 | `boundary` | 与邻近概念如何区分，最容易误会什么。 |
| 具体例子 | `resourceIds[]` | 引用资源正本。 |
| 依据 | `sourceIds[]` | 引用来源 ID；自行设计的例子在核对说明中标清。 |

## 关系条目

| 写什么 | JSON 字段 | 填写说明 |
|---|---|---|
| 稳定标识 | `id` | 用于定位和修正这条关系。 |
| 起点与终点 | `from`、`to` | 引用对象 ID。 |
| 类型 | `type` | 当前支持 `implements` 和 `comparable`。 |
| 显示含义 | `label` | 读者能读懂的一句话，不能只写“相关”。 |
| 适用条件 | `condition` | 写明谈的是哪种能力或需求，以及不能推出什么结论。 |
| 依据 | `sourceIds[]` | 引用支持关系及其条件的来源。 |

`implements` 从具体资源指向概念，表示提供能力或采用某种运行方式。`comparable` 在两个资源之间表示可以围绕某个需求进行比较；它不表示可直接替换。本轮关系用法的边界见 [sources.md](sources.md)。

同一条实现关联必须同时出现在资源的 `conceptIds`、概念的 `resourceIds` 和 `implements` 关系中；校验器逐对核对三者，防止列表有对象但详情缺少关系说明。

## 来源与入口

新增来源写入 `sources`：`id`、`title`、`url`、`checkedAt`。URL 指向实际核对的官方页面；日期为实际核对日，不能把访问日期写成文档发布日期。

入口写入 `routes`，只保存 `id`、`title`、`relation`、`steps[]`、`conceptId`、`resourceIds[]`。本轮三入口是 `home` / `domains` / `products`，分别表示 `role` / `domain` / `product`。`steps` 固定为“入口名称／分支名称／主题概念”三层；路径文字不同，但样板都通向同一个 `data-storage` 概念及同一组资源。

不要在入口内增加资源正文或官方链接字段。资源更新一次，三条路径应同时展示最新说明。

## 提交例子一：新增资源

以本轮加入 `postgresql` 的方式为例，实际内容以 [content.json](content.json) 为准：

1. 在 `sources` 登记核对过的官方页面，随后在 `resources` 填一条完整资源记录。
2. 通过 `conceptIds` 指向相关概念，在概念的 `resourceIds` 中补入同一资源 ID；关系单独记录到 `relations`。
3. 本轮三入口共享一个样板主题，因此各自的 `resourceIds` 都引用 `postgresql`，而不复制该资源对象。
4. 在 [sources.md](sources.md) 写清新增来源支持哪些说明，构建后从三个入口验证同一条卡片。

PR 说明可以写：“补入资源 `postgresql`，让读者能从独立数据库服务的运行方式继续找到官方资料。正文与条件见该资源记录，新增来源及说明范围见 `sources.md`。已从三个入口核对共享详情。”

## 提交例子二：修正关系

以 `sqlite-postgresql-comparison` 为例，若旧文案让读者误以为二者能无条件替换：

1. 定位这条关系，保留两端稳定 ID，重写 `label` / `condition`，把比较的需求和不能直接推出的结论说明白。
2. 重新核对相关官方页面，更新受影响的来源与资源核对日期，并同步 [sources.md](sources.md) 的支撑范围。
3. 保持资源卡正文只在正本中出现一次；检查两个资源的详情都没有继续暗示无条件替换。

PR 说明可以写：“修正 `sqlite-postgresql-comparison` 的比较条件，避免将同类理解为直接替换。条件与来源只维护在现有关系记录；已检查两个详情入口中的呈现。”

这两段是提交描述示例，不是第二份数据库事实正文。实际修改必须来自所核对的资料，不能只套用例句。

## 提交说明

```markdown
改动对象：资源／概念／关系的 ID
读者原来会遇到的问题：
修改后能看懂或找到什么：
依据：对应 sourceIds，官方页面支持的范围
涉及的入口：引用哪些既有 ID；是否改变路径
验证：构建与检查结果，实际走过哪些路径
仍有待确认的内容：没有则省略
```

在仓库根目录运行 `node design/build.mjs` 更新样板，运行 `node design/build.mjs --check` 检查内容、语法与产物同步；`node design/checks.mjs` 验证校验器能拒绝坏数据。机械检查通过不替代来源核对，也不等于解释已经教会读者。
